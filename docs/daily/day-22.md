## 데이터 분리와 접근 조건

- `privateState/server`: 전체 `ServerGameState`를 보관한다. 덱 순서와 모든 참가자의 예약 카드 ID를 포함하므로 클라이언트의 읽기·쓰기를 모두 거부한다.
- `game/publicState`: 서버 상태에서 허용한 필드만 새 객체로 만든다. 시장 카드 ID·은행·점수·공개 귀족은 포함하고, 덱은 **장수만**, 각 참가자의 예약 카드는 **장수만** 포함한다. 방 참가자만 문서 하나를 읽을 수 있다.
- `privatePlayers/{uid}`: 해당 참가자의 예약 카드 ID만 포함한다. 로그인한 본인이 현재 방 참가자일 때 그 문서 하나만 읽을 수 있다. 컬렉션 목록 조회와 모든 클라이언트 쓰기는 거부한다.
- `initializeGameViews`는 Admin SDK로 시작한 2~4인 방을 읽고, 전체 상태·공개 뷰·개인 뷰를 한 트랜잭션에서 **한 번만** 만든다. 대기 중인 방이나 중복 초기화는 거부한다. 이 함수는 웹 앱에서 호출할 수 있는 API로 노출하지 않는다.

## 검증 명령

`npm run test:views`는 엔진·Functions 패키지를 빌드한 뒤 Auth·Firestore 에뮬레이터에서 위 접근 조건을 검증한다. `npm test`는 엔진의 공개·개인 뷰 테스트를 포함한다.

## 작업 기록
- 구현 내용: 공개·개인 상태 투영, 신뢰 서버용 초기화 함수, 클라이언트 읽기 서비스, 세 종류의 Firestore 문서 권한 규칙을 추가했다. 엔진 출력은 Node 서버에서도 불러올 수 있도록 ESM 경로를 정리했다.
- 실행한 테스트/결과: `npm run test:views`, `npm run test:rooms`, `npm run typecheck`, `npm run build`, `npm test` 통과(엔진 79개·웹 1개). 실제 프로젝트의 변경 규칙은 아직 게시하지 않았다.
- 이슈/의사결정: 현재 Spark/Blaze 없는 실서비스에는 Admin SDK 초기화 함수를 호출할 신뢰할 수 있는 서버가 없다. 방장은 21일차에 `playing` 상태까지 바꿀 수 있지만, 실제 덱·시장·개인 예약 문서는 생성되지 않는다. 클라이언트에 서버 상태나 덱 생성 권한을 주면 비밀과 규칙 검증을 보장할 수 없어 허용하지 않았다.
- 다음 작업에 전달할 사항: 23~24일차의 `submitAction`과 멱등성도 신뢰할 수 있는 서버 실행 경로가 필요하다. 운영 방식이 정해지기 전까지 이 함수와 비공개 문서 작성은 에뮬레이터의 Admin SDK 검증 범위다.
