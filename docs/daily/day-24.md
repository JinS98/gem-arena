## 처리 방식

- 성공한 행동은 `rooms/{roomCode}/actionReceipts/{uid}/actions/{actionId}`에 정규화한 `expectedVersion`·`action`과 성공 응답을 보관한다. 처리 기록은 서버 전용이며 클라이언트 읽기·쓰기를 거부한다. `actionId`는 영문·숫자·`_`·`-` 1~128자로 제한한다.
- 서버는 인증·방 참가 여부를 확인한 뒤 처리 기록을 먼저 검사한다. 같은 사용자·방·ID에 **같은 요청**이면 저장된 성공 응답을 반환하고 상태를 쓰지 않는다. 내용이나 `expectedVersion`이 다르면 `ACTION_ID_REUSED`로 거부한다.
- 새 ID이면 서버 상태의 `expectedVersion`을 확인한다. 엔진 규칙을 통과한 새 상태, 공개 뷰, 모든 참가자의 개인 뷰, 처리 기록을 **한 트랜잭션**에서 기록한다. 서로 다른 요청이 같은 버전으로 경쟁하면 하나만 성공하고 다른 하나는 재검사 후 `VERSION_CONFLICT`가 된다.
- 실패한 요청은 처리 기록을 남기지 않는다. 호출자는 네트워크 재시도 시 동일한 `actionId`·`expectedVersion`·`action`을 유지해야 한다. 처리 기록은 사용자별로 분리하며, 더 이상 방 참가자가 아니면 이전 성공 응답도 조회할 수 없다.

## 검증 시나리오
| 입력·조건 | 기대 결과 | 실행 결과 |
|---|---|---|
| 같은 `actionId`·내용 재전송 | 첫 성공 응답 반환, 버전 불변 | 에뮬레이터 통과 |
| 같은 ID로 다른 행동·버전 제출 | `ACTION_ID_REUSED`, 상태 불변 | 에뮬레이터 통과 |
| 같은 요청 2건 동시 제출 | 모두 같은 결과, 상태 1회 변경 | 에뮬레이터 통과 |
| 서로 다른 ID·같은 버전 동시 제출 | 1건 성공, 1건 `VERSION_CONFLICT` | 에뮬레이터 통과 |
| 경로 구분자가 포함된 `actionId` | `INVALID_ACTION`, 처리 기록 없음 | 에뮬레이터 통과 |
| 다른 턴까지 진행한 뒤 과거 성공 요청 재전송 | 과거 응답 반환, 현재 버전 불변 | 에뮬레이터 통과 |
| 클라이언트의 처리 기록 읽기·쓰기 | 모두 거부 | 에뮬레이터 통과 |
| 방 상태가 `waiting`으로 변경 | 신규 행동 거부, 상태 불변 | 에뮬레이터 통과 |

## 작업 기록
- 구현 내용: 23일차 트랜잭션에 사용자별 `actionId` 처리 기록 읽기·생성을 추가했다. 중복 요청은 성공 응답을 재생하고, ID 재사용·버전 충돌을 구분한다. Firestore 규칙에 처리 기록 접근 거부를 명시했다.
- 실행한 테스트/결과: `npm run test:actions`, `npm run typecheck`, `npm run build`, `npm test` 통과(엔진 79개·웹 1개). 같은 요청과 경쟁 요청을 동시 호출하고 서버·공개·개인 상태 버전과 처리 기록을 확인했다.
- 이슈/의사결정: 실서비스에는 22일차 게임 초기화 서버와 23~24일차 Callable이 아직 연결·배포되지 않았다. 새 규칙도 실제 프로젝트에 게시하지 않았다. 따라서 실제 화면에서는 여전히 방의 `playing` 상태까지만 확인할 수 있다.
- 다음 작업에 전달할 사항: 25일차 실시간 구독은 공개·본인 개인 뷰를 대상으로 한다. 실제 멀티 게임 진행에는 비공개 초기화와 행동 처리를 실행할 신뢰 서버 운영 방식이 필요하다.
