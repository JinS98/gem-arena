## 입력·출력·예외 조건

- `setReady(roomCode, ready)`: 로그인한 방 참가자만 본인의 `players.{uid}.ready`를 변경한다. 대기 중인 방에서만 허용하며, 같은 값 재요청은 상태를 바꾸지 않는다. 다른 사람의 준비 상태나 방 정보는 수정할 수 없다.
- `startGame(roomCode)`: 방장만 호출한다. 참가자 2~4명이 모두 준비했을 때 `status`를 `playing`으로 바꾸고 `startedAt`을 기록한다. 인원 부족, 미준비, 비방장, 중복 시작은 거부한다.
- 모든 상태 전이 조건은 Firestore 규칙에서 현재 문서와 요청 결과를 원자적으로 검사한다. 준비 또는 참가가 시작과 동시에 들어오더라도 성공한 순서의 조건을 다시 검사한다.
- 대기실은 실시간 구독으로 참가자별 준비 표시와 시작 가능 여부를 갱신한다. 시작 후 신규 참가와 준비 변경을 막는다.

## 작업 기록
- 구현 내용: Firestore SDK의 `setReady`·`startGame`, 대기실 준비 버튼과 방장 시작 버튼, 본인 준비·방장 시작 전용 보안 규칙을 추가했다. Cloud Functions나 Blaze 요금제는 이 단계에 필요하지 않다.
- 실행한 테스트/결과: `npm run test:rooms`와 `npm run typecheck` 통과. 위 검증 시나리오를 Auth·Firestore 에뮬레이터에서 확인했다.
- 이슈/의사결정: 초기 게임 상태·비공개 덱·실제 턴 API는 아직 연결되지 않았다. 이 단계의 시작은 방 상태 전환이며, 대기실에 후속 작업 안내를 표시한다. 사용자 승인 후 변경된 Firestore 규칙을 실제 `gem-arena` 프로젝트에 게시했다. 사용자가 준비 완료 후 시작 버튼을 눌러 `게임 중` 표시까지 직접 확인했다.
- 다음 작업에 전달할 사항: 22일차에는 `playing` 상태가 된 방의 공개/비공개 게임 데이터 구조와 접근 규칙을 설계한다. 현재 `rooms/{roomCode}` 문서의 `players` 맵과 `startedAt`을 기준으로 이어간다.
