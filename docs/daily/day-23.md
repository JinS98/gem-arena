# 23일차 — submitAction 인증·턴·규칙 검증

**단계:** 멀티플레이  
**예상 시간:** 3~4시간  
**상태:** 로컬 구현·검증 완료, 실서비스 미연결

## 오늘의 목표
인증한 방 참가자만 자신의 차례에 유효한 게임 행동을 제출하고, 서버가 게임 엔진 규칙으로 검증한 결과만 확정한다.

## 입력·출력·검증

- 입력은 `roomId`, `actionId`, `expectedVersion`, `action`이다. 방 ID는 8자리 코드, 버전은 0 이상의 안전한 정수, 행동은 타입별 허용 필드로 제한한다. `TIMEOUT`은 서버 내부 처리용이므로 클라이언트 요청에서 거부한다.
- 사용자 UID는 요청 본문을 신뢰하지 않고 Callable의 인증 정보에서 얻는다. 방 참가자 명단과 플레이어 데이터에 모두 속하고 기권하지 않은 사용자만 진행할 수 있다.
- 방이 `playing`이고 서버 전용 상태가 존재해야 한다. 방과 서버 상태의 참가 순서, 현재 버전, 차례를 확인한 뒤 게임 엔진의 `reduceGameAction`이 행동 규칙을 검증한다.
- 성공하면 한 Firestore 트랜잭션에서 서버 전용 상태, 공개 뷰, 각 참가자의 개인 뷰를 갱신한다. 응답은 새 `version`, `phase`, `turnIndex`만 반환하며 비공개 카드·덱 정보는 담지 않는다.
- `actionId`는 입력 형식만 검증한다. 같은 ID의 이전 응답 재생과 재시도 멱등성은 24일차 범위다. 현재 같은 버전으로 다시 보내면 `VERSION_CONFLICT`가 발생한다.

## 검증 시나리오
| 입력·조건 | 기대 결과 | 실행 결과 |
|---|---|---|
| 비로그인·비회원 요청 | `UNAUTHENTICATED`·`NOT_ROOM_MEMBER` | 에뮬레이터 통과 |
| 다른 플레이어 차례 | `NOT_YOUR_TURN` | 에뮬레이터 통과 |
| `TIMEOUT`·불법 보석 조합 | `INVALID_ACTION` | 에뮬레이터 통과 |
| 현재 상태와 다른 버전 | `VERSION_CONFLICT`, 상태 불변 | 에뮬레이터 통과 |
| 정상 보석 획득 | 다음 차례와 버전 1, 서버·공개·개인 뷰 동시 갱신 | 에뮬레이터 통과 |
| 비공개 덱 카드 예약 | 본인 개인 뷰에만 카드 ID, 공개 뷰에는 예약 장수만 | 에뮬레이터 통과 |
| 방이 다시 대기 상태 | `GAME_NOT_STARTED`, 상태 불변 | 에뮬레이터 통과 |

## 완료 기준
**잘못된 턴과 액션을 서버가 거부한다** — Auth·Firestore·Functions 에뮬레이터에서 확인했다.

## 작업 기록
- 구현 내용: 인증된 Callable 진입점, 타입별 요청 검증, 방 멤버십·차례·버전 검사, 엔진 규칙 적용 및 공개·개인 상태의 원자적 갱신을 추가했다. 웹 호출 서비스는 `actionId`를 호출자가 지정하도록 한다.
- 실행한 테스트/결과: `npm run test:actions`, `npm run typecheck` 통과. 정상·거부 응답과 비공개 예약 정보 노출 여부를 검증했다.
- 이슈/의사결정: 첫 테스트에서 같은 색 보석 2개 받기를 불법으로 가정했으나, 은행에 해당 색이 4개 이상이면 합법이므로 불법 조합을 3개 중 중복 색으로 바꿨다. 실제 Firebase 프로젝트에는 신뢰 서버/Cloud Functions가 연결되지 않았고, 이 Callable도 배포하지 않았다. 브라우저는 서버 전용 문서를 직접 쓸 수 없다.
- 다음 작업에 전달할 사항: 24일차에 `actionId` 기록과 같은 요청의 성공 응답 재생, 다른 본문으로 ID 재사용 거부, 동시 요청 검증을 추가한다. 실제 멀티 게임판을 진행하려면 22일차 초기화와 이번 Callable을 실행할 신뢰 서버 운영 방식이 먼저 필요하다.
