## 검증 시나리오
| 입력·조건 | 기대 출력 | 실행 결과 |
|---|---|---|
| 구매 카드 ID 목록 | 보너스 색별 영구 할인 수량 | 통과 |
| 색별 비용보다 적거나 많은 할인 | 남은 비용을 색마다 `max(0, 비용 - 할인)`으로 계산 | 통과 |
| 일반·황금 보석 혼합 결제 | 남은 비용과 정확히 일치하면 보석을 은행에 반환 | 통과 |
| 일반 보석을 보유한 색에 황금 사용 | 정확한 총결제면 허용 | 통과 |
| 할인 후 비용 0 | 보석 0개 결제만 허용 | 통과 |
| 부족·초과·잘못된 색·미보유 보석 결제 | 거부, 원본 은행·보유량 유지 | 통과 |
| 중복/없는 카드 ID, 음수·소수·누락/여분 수량 | 거부 | 통과 |

## 입력·출력·예외 조건

- 입력: `countCardBonuses(purchasedCardIds)`에는 구매 완료된 카드 ID만 전달한다. `remainingCardCost(cost, bonuses)`는 일반 보석 5색의 비용·할인을 받는다. `canPayForCard`와 `payForCard`는 추가로 6종의 보유량·결제량을 받고, `payForCard`는 은행 수량도 받는다.
- 출력: 색별 남은 비용은 0 미만이 되지 않는다. 결제가 유효하면 `payForCard`가 제출한 일반 보석과 황금을 플레이어에서 은행으로 옮긴 새 수량을 반환한다. 입력 객체는 변경하지 않는다.
- 예외: 중복·없는 구매 카드 ID, 잘못된 비용/할인, 음수·소수·누락/여분 보석 수량, 보유량 초과, 부족·초과·잘못된 색 결제를 거부한다. 황금은 보유한 일반 보석이 있는 색에도 사용할 수 있지만 남은 비용만 정확히 메워야 한다. `canPayForCard`는 불가 시 `false`, 나머지 계산·결제 함수는 잘못된 입력에 `RangeError`를 사용한다.

## 작업 기록
- 구현 내용: 구매 카드 ID에서 영구 할인을 세고 색별 남은 비용을 계산한다. 일반 보석·황금 결제의 정확성 및 보유량을 검증하고, 결제한 보석을 은행으로 이동하는 순수 함수를 추가했다. README와 규칙 문서에 범위를 반영했다.
- 실행한 테스트/결과: `npm test` 33개 통과(8일차 결제 8개 포함), `npm run typecheck` 및 `npm run build` 통과.
- 이슈/의사결정: 황금은 해당 색 일반 보석을 보유해도 사용 가능하다. 할인 초과분은 보석으로 돌려받지 않는다. 결제에는 정확한 6종 수량이 필요하다. 카드 소유·점수·시장 갱신은 결제와 분리해 9일차에 연결한다.
- 다음 작업에 전달할 사항: 9일차 구매 로직은 결제 전에 플레이어의 기존 `purchasedCardIds`로 할인량을 계산하고 `payForCard` 결과를 적용한다. 결제 성공 후에만 카드 ID·점수·시장/예약 상태를 바꾼다. 서버 API는 `RangeError`를 규칙 위반으로 매핑해야 한다.
