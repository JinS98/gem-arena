## 검증 시나리오
| 입력·조건 | 기대 출력 | 실행 결과 |
|---|---|---|
| 공개 카드 ID 예약 | 해당 칸 보충, 예약 목록 추가, 황금 1개 지급 | 통과 |
| 비공개 덱 단계 예약 | 덱 맨 앞 ID만 예약자 목록에 추가, 시장·타인 목록 불변 | 통과 |
| 예약 2장/3장 보유 | 세 번째 허용/추가 예약 거부 | 통과 |
| 황금 은행 0개 | 카드만 예약, 황금 미지급 | 통과 |
| 황금 수령 후 11개 보유 | `excess: 1`, 정확한 반환 가능 | 통과 |
| 공개 카드 예약 후 덱 소진 | 시장 칸 `null`, 네 칸 유지 | 통과 |
| 잘못된 대상·턴·단계·보석 상태·빈 덱·반복 공개 예약 | 거부, 원본 상태 불변 | 통과 |

## 입력·출력·예외 조건

- 입력: `reserveCard(state, playerId, action)`은 서버 전용 전체 상태, 현재 플레이어 UID, `RESERVE_CARD` 행동을 받는다. `cardId`(공개 시장)와 `level`(비공개 덱) 중 정확히 하나만 지정해야 한다. 예약은 3장 미만이고 대상 카드가 존재해야 한다.
- 출력: 새 서버 상태와 `excess`를 반환한다. 공개 예약은 시장의 같은 칸을 덱 맨 앞 카드로 보충하고, 비공개 예약은 시장을 변경하지 않는다. 은행에 황금이 있으면 플레이어에게 1개 이동한다. 입력 상태는 변경하지 않는다.
- 예외: 잘못된 턴·단계·대상·보석 상태·예약 한도 초과·빈 덱은 `RangeError`로 거부한다. 황금이 없으면 예약은 계속 허용한다. 반환된 상태에는 모든 예약 ID가 있으므로 클라이언트에 전송하면 안 된다. `excess > 0`일 때의 `discarding` 단계와 턴·버전 변경은 후속 reducer에서 처리한다.

## 작업 기록
- 구현 내용: 공개 시장 또는 덱 맨 위 카드 예약, 시장 보충, 3장 제한, 황금 1개 조건부 지급과 초과 보유량 계산을 추가했다. README·데이터 모델·규칙 문서에 서버 전용 상태 조건을 반영했다.
- 실행한 테스트/결과: `npm test` 47개 통과(10일차 예약 7개 포함), `npm run typecheck` 및 `npm run build` 통과.
- 이슈/의사결정: 비공개 덱 카드는 예약자 `reservedCardIds`에만 이동한다. 다만 `ServerGameState` 자체에는 덱과 모든 예약 ID가 있으므로 공개 전송은 금지한다. 공개 뷰/개인 상태 분리는 22일차 범위다. 순수 예약 함수는 턴·버전을 변경하지 않으며 `excess`만 반환한다.
- 다음 작업에 전달할 사항: 13일차 reducer에서 `excess > 0`이면 `discarding` 단계로 이동하고 반환 후 턴을 끝낸다. 22일차 상태 분리에서는 덱 순서와 타인 예약 카드 ID를 공개 뷰에서 제거한다. 24일차에는 동일 `actionId` 재전송에 대한 멱등성을 적용한다.
