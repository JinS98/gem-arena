## 검증 시나리오
| 입력·조건 | 기대 출력 | 실행 결과 |
|---|---|---|
| 은행에 3색 이상 / 1~2색만 남음 | 정확히 서로 다른 3색 / 남은 색에서 1~2색 허용 | 통과 |

| 황금 포함해 초과분 정확히 반환 | 최종 보유량 10개, 은행 수량 복구 | 통과 |
| 초과가 없거나 부족·과다·미보유 보석 반환 | 거부, 원본 상태 유지 | 통과 |

## 입력·출력·예외 조건

- 입력: `canTakeGems(bank, colors)`와 `takeGems(bank, gems, colors)`는 은행·보유량과 일반 보석 색 배열을 사용한다. 서로 다른 세 색이 있으면 정확히 세 색을 받고, 같은 색 두 개는 행동 직전 재고가 4개 이상이어야 한다. `discardExcessGems(bank, gems, returned)`에는 일반 보석·황금 보석 6종의 반환량을 전달한다.
- 출력: `takeGems`는 새 `bank`, `gems`, `excess`를 반환한다. 보유량 10개를 넘지 않으면 `excess`는 0이다. `discardExcessGems`는 초과량을 정확히 반환한 새 은행·보유량을 반환한다. 모든 함수는 입력을 변경하지 않는다.
- 예외: 획득 불가 조합과 잘못된 보석 수량은 `RangeError`로 거부한다. 반환은 초과량과 정확히 일치하고 실제 보유량을 넘지 않아야 하며, 초과가 없는 상태에서는 거부한다. `canTakeGems`는 잘못된 입력에 `false`를 반환한다. 인증·턴·버전 검사는 이후 reducer/API 단계에서 처리한다.

## 작업 기록
- 구현 내용: 기존 획득 가능 여부 검사에 보석 수량 검증을 보강하고, 보석 획득·초과량 계산·정확한 반환 순수 함수를 추가했다. README와 규칙 문서에 사용 방식을 반영했다.
- 실행한 테스트/결과: `npm test` 25개 통과(보석 규칙 13개 포함), `npm run typecheck`와 `npm run build` 통과.
- 이슈/의사결정: 황금 보석도 10개 한도와 반환 선택에 포함한다. 보석 획득 직후에는 10개 초과 상태를 허용하며 `excess`로 필요한 반환 수량을 알려준다. 반환을 마칠 때까지 턴을 넘기지 않는 `discarding` 단계는 후속 상태 전이에 연결한다. 첫 타입 검사에서 배열 타입 좁히기 오류가 나 수정 후 통과했다.
- 다음 작업에 전달할 사항: 8일차 구매 비용·결제는 같은 6색 `Inventory`를 사용한다. 10일차 예약으로 받은 황금도 `excessGemCount`를 거치고, 13일차 reducer는 `excess > 0`이면 `discarding`으로 이동해 정확한 반환 후 턴 마무리를 진행한다. 서버는 `RangeError`를 규칙 위반 응답으로 매핑해야 한다.
