## 입력·출력·예외 조건

- **입력:** 2·3·4명의 독립 익명 계정과 브라우저 저장 공간, 준비된 Auth·Firestore·Functions 에뮬레이터, 에뮬레이터 모드 Vite 서버, Chrome을 사용한다. 테스트마다 새로운 방을 만든다.
- **출력:** 방 생성·참가·준비·시작 후 모든 화면이 게임판으로 이동한다. 각 턴의 공개 상태는 모든 참가자에게 같고, 개인 예약 카드는 소유자에게만 보인다. 15점 최종 라운드가 끝나면 서버와 화면에 같은 승자가 표시된다.
- **예외:** 타인의 개인 문서 읽기는 `permission-denied`여야 한다. 예약 카드 ID가 타인 화면에 노출되지 않아야 한다. PC 1440×900과 모바일 390×844에서 문서 가로 넘침이 없어야 한다. 기존 권한·중복 요청 검증은 회귀 테스트로 유지한다.

## 검증 시나리오
1. 정상 흐름이 기대한 결과를 반환하는지 확인한다.
2. 잘못된 입력 또는 권한이 거부되는지 확인한다.
3. 게임 상태를 바꾸는 작업이라면 중복 요청·경계값을 검증한다.
4. 독립 브라우저 저장 공간에서 공개 게임판이 같은 서버 확정 상태를 보여주고, 각 플레이어의 개인 영역만 본인에게 보이는지 확인한다. 물리적으로 다른 기기에서는 추가 확인이 필요하다.

## 재실행 방법

- 자동 에뮬레이터 실행과 2~4인 서버 완주: `npm run test:complete`
- 브라우저 완주: 터미널 1에서 `npm run emulators`, 터미널 2에서 `npm run dev:emulators`, 터미널 3에서 `npm run test:browser-complete`
- 이미 에뮬레이터가 실행 중이면 충돌 없이 `node apps/web/scripts/verify-multiplayer-complete.mjs`로 서버 완주를 다시 실행한다. 브라우저 스크립트는 자체 임시 Chrome 세션을 띄운다. 필요하면 `CHROME_PATH`, `GEM_ARENA_WEB_URL`, `CHROME_DEBUG_PORT`를 설정한다.

## 읽기·성능 측정

실행 중인 로컬 에뮬레이터에서 각 참가자의 공개 문서 1개와 본인 개인 문서 1개를 구독했다. `문서 전달`은 캐시·메타데이터 이벤트를 제외한 실제 버전별 구독 수신 횟수다. `p95`는 한 행동의 Callable 응답 및 모든 구독자가 같은 버전을 받을 때까지의 시간을 각각 측정했다.

| 인원 | 행동 수 | 문서 전달 | 전달 데이터 | Callable p95 | 전체 구독 동기화 p95 |
|---:|---:|---:|---:|---:|---:|
| 2 | 55 | 224 | 144 KB | 41 ms | 79 ms |
| 3 | 79 | 480 | 395 KB | 44 ms | 79 ms |
| 4 | 100 | 808 | 797 KB | 42 ms | 79 ms |

현재 구조에서 모두 접속한 `P`명과 `A`번의 행동에 대해 게임판 문서 전달은 `2 × P × (A + 1)`회다. 각 참가자가 공개 상태와 본인 개인 상태를 한 문서씩 받기 때문이다. 전달 데이터는 수신 문서를 JSON으로 직렬화한 크기로, 실제 네트워크 전송량과 다르다. `submitAction` 트랜잭션은 행동마다 방·서버 상태·영수증 문서 3개를 읽고, 서버 상태·공개 상태·참가자별 개인 상태·영수증을 쓴다. 종료 행동은 방 상태도 갱신한다. 위 수치는 **에뮬레이터의 관측값**이며 실제 Firestore 청구 읽기 수나 네트워크 지연을 뜻하지 않는다. 재연결·여러 탭·쿼리 규칙·서버 트리거가 있으면 운영 비용은 달라진다.

## 작업 기록
- 구현 내용: `verify-multiplayer-complete.mjs`가 2~4인 게임을 실제 Callable로 매 턴 제출하고 모든 참가자의 공개·개인 구독을 서버 상태와 비교한다. 예약 카드의 타인 읽기 거부, 중복 없는 버전 진행, 종료 결과와 지연 시간·전달량을 기록한다. `verify-multiplayer-browser.mjs`는 독립 Chrome 세션으로 실제 방 생성·참가·준비·자동 이동부터 승리 모달까지 진행한다. 예약·보석 받기·시장 카드 구매는 화면 버튼으로 제출하고 피드백을 확인한다. 나머지 턴은 같은 브라우저 계정의 인증으로 Callable을 제출하며 화면 상태를 주기적으로 확인한다.
- 실행한 테스트/결과: `npm test` 엔진 84건·웹 1건, `npm run build`, 2·3·4인 서버 완주와 브라우저 완주 모두 통과했다. 브라우저 실행에서 2인 55행동, 3인 77행동, 4인 88행동으로 종료했다. PC와 390px 모바일에서 상대 패널·은행·본인 예약 카드 표시 및 가로 넘침 0건을 확인했다. 타인 예약 카드 ID의 DOM 노출도 확인되지 않았다.
- 이슈/의사결정: 첫 브라우저 실행은 Vite가 IPv6 `localhost`에만 바인딩된 상태에서 `127.0.0.1`로 접근해 실패했다. 브라우저 URL을 `localhost`로 수정했다. 준비 직후 방장 버튼 활성화를 기다리지 않으면 시작 클릭이 무시되는 경합도 발견해 검증 스크립트에서 버튼 활성화와 서버 `playing` 상태를 순서대로 확인한다. 테스트는 헤드리스 Chrome과 로컬 에뮬레이터의 성능이며 실서비스 지연·청구량의 대표값으로 사용하지 않는다.
- 다음 작업에 전달할 사항: 31일차에는 실제 배포 환경의 규칙·Functions·Hosting 연결과 운영 읽기/쓰기 지표를 확인한다. 서로 다른 물리 기기와 320px 이하·저사양 기기의 완주 및 장시간 재연결 비용은 추가 검증이 필요하다.
