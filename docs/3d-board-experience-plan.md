# Gem Arena 입체 보드게임 경험 제안

작성일: 2026-10-23. 코드와 문서를 검토한 설계 제안이며, 실제 3D 구현이나 성능 측정 결과가 아니다. 예상 이미지는 생성형 콘셉트로 실제 화면 캡처와 구분한다.

## 권장 방향

먼저 기존 React 화면에 2.5D 재질·두께·그림자와 행동 연출·효과음을 적용한다. 실제 3D가 주는 차이가 필요한지 확인한 후 테이블·칩·덱을 WebGL로 옮긴다. 목표는 카드 정보를 읽으면서 실물 부품을 집고 내려놓는 느낌이다.

카드 시장은 3단계 × 4장, 단계별 덱, 귀족, 6색 은행, 상대 공개 현황, 본인 보유 보석·영구 할인·비공개 예약으로 유지한다. 기본 테마의 네이비·차콜·앤틱 골드를 펠트·호두나무·금속·종이 재질로 확장한다. 기존 팬 테마는 카드 그림·자원 아이콘 스킨으로 연결한다.

## 현재 프로젝트에서 확인한 기반

| 영역 | 현재 상태 | 활용 및 개선 |
|---|---|---|
| 게임 규칙 | `packages/game-engine`의 순수 상태 전이·비용 계산·뷰 변환 | 시각 표현과 분리되어 있어 재사용 가능 |
| 온라인 서버 | `functions`에서 행동·턴·버전 검증 | 연출과 별개로 서버 확정 결과를 기준으로 유지 |
| 실시간 구독 | `services/gameViews.ts`에서 공개/개인 문서 버전 일치 후 게시 | 동일한 확정 상태를 DOM/3D 렌더러에 공급 |
| 온라인 화면 | `MultiplayerGamePage.tsx` 655줄, 통신·입력·연출·배치 결합 | 상태 연결과 보드 표시 컴포넌트부터 분리 |
| 로컬 화면 | `GameBoardPage.tsx` 267줄, Zustand 상태와 보상 연출 | 로컬 프로토타입 후 온라인에 공통 보드 적용 |
| 카드·부품 | `MarketCard`, `DeckCard`, `NobleGallery`, `GemIcon`, `GemBank`, `PlayerPanel` | 기존 그림 재사용, 부품 재질과 두께 추가 |
| 움직임 | `animations/boardReward.ts`, `marketDeal.ts`에서 DOM 복제와 Web Animations 사용 | 이동 궤적·착지·뒤집기·효과음 확장 |
| 스타일 | `styles.scss` 1,101줄, 그라디언트·그림자·hover 이동 구현 | 테이블/부품/화면 HUD 스타일 분리, 재질 토큰 도입 |
| 접근성 | 카드 버튼·키보드 초점·모달 초점 유지·움직임 줄이기 분기 존재 | 기존 입력 방식을 유지하면서 입체 표현 추가 |
| 소리·3D | 웹 패키지에 Three.js/R3F 없고, 별도 소리 모듈 미발견 | 필요한 단계에서 도입 |

문서 일부는 과거 시점의 타이머·배포 상태를 기술한다. 이 제안의 구현 판단은 현재 코드에 있는 온라인 턴 제한·확정 버전 처리 등을 우선한다. 이번 검토에서 운영 배포 상태는 확인하지 않았다.

## 예상 이미지 세 방향

저장된 이미지: [A — 2.5D](assets/3d-board-concepts/01-tactile-2-5d.png), [B — 테이블형 3D](assets/3d-board-concepts/02-tabletop-3d.png), [C — 구매 연출](assets/3d-board-concepts/03-purchase-moment.png).

1. **A — 기존 화면을 살린 2.5D:** 거의 위에서 보는 펠트 보드, 얇은 종이 단면, 겹쳐진 덱, 쌓인 칩, 일정한 광원. 정보 패널과 비용 숫자는 정면으로 읽힌다. 첫 구현 권장안.
2. **B — 실제 테이블형 3D:** 테이블에 앉은 카메라, 목재 프레임, 칩 트레이, 입체 덱. 카드 12장을 모두 읽을 수 있게 기울기는 제한하고 확대 보기를 제공한다. 중기 확장안.
3. **C — 구매 순간:** 선택 카드가 살짝 들리고, 결제 칩이 은행으로 돌아가며, 획득 보너스가 개인 트레이에 도착한다. 빈 시장 슬롯에는 새 카드가 배분·공개된다. A/B에 공통 적용할 상호작용 목표.

콘셉트 이미지의 작은 글자·비용·보석 수량은 규칙 검증용이 아니다. 최종 UI에서는 실제 게임 데이터와 HTML 텍스트로 표현한다.

## 생생함을 만드는 행동 설계

| 상황 | 제안 연출 | 권장 길이 초안 |
|---|---|---|
| 카드 탐색 | 마우스 위치에 따라 2~4도 기울기, 6~10px 들어 올림, 그림자 확장 | 120~180ms |
| 카드 확인 | 카드 확대와 원래 비용/실제 결제 비용 표시, 모바일은 탭으로 열기 | 180~250ms |
| 보석 선택 | 칩이 살짝 들려 선택 트레이에 모이고 수량 표시 | 120~200ms |
| 보석 획득/반환 | 확정 후 곡선 이동, 작은 회전, 짧은 착지·칩 소리 | 350~550ms |
| 카드 구매 | 확정 후 결제 칩 반환 → 카드/보너스 획득 → 빈자리 보충 | 총 700~1,000ms 목표 |
| 예약 | 시장 카드는 본인 예약 트레이로, 상대에게는 카드 뒷면만 이동 | 400~650ms |
| 귀족 방문 | 귀족 타일이 앞으로 나온 뒤 점수 영역으로 이동 | 600~900ms |
| 턴 교체 | 다음 좌석 테두리·작은 턴 마커·선택적 알림음 | 200~350ms |

시간은 디자인 초안이다. 기존 연출에 효과를 단순 누적하면 조작 대기가 길어지므로 병렬 실행과 축약을 사용한다. 자동 카메라 회전·상시 흔들림·큰 입자 폭발은 기본 연출에서 제외한다.

## 구현 방식 비교

| 방식 | 적합한 결과 | 프로젝트 영향 | 판단 |
|---|---|---|---|
| CSS 2.5D + 현재 애니메이션 | 두께·층·광택·고정 시점의 테이블 | 기존 DOM과 테스트·접근성 재사용 폭이 큼 | 우선 적용 |
| R3F/Three.js + HTML HUD | 실제 광원·입체 칩·테이블·덱 | 좌표·선택 판정·자산·모바일 품질 관리 필요 | 2차 검증 후 선택 |
| 게임 화면 전체 3D 전환 | 자유로운 공간·카메라 | 텍스트·입력·대화상자까지 재설계 범위 큼 | 현 단계 우선순위 낮음 |

CSS는 `perspective`, `transform-style: preserve-3d`, 레이어별 변환으로 입체감을 만들 수 있다. `overflow`, `filter`, `opacity` 등의 조합은 레이어를 평면화할 수 있어 카드 바깥 입체 래퍼와 안쪽 이미지 자르기 레이어를 분리한다.

3D를 도입하면 테이블 위 부품은 Canvas, 이름·수량·시간·버튼·모달은 HTML HUD로 구성한다. 고정 카메라부터 시작하고, 대기 중에는 demand 렌더링, 움직이는 동안에는 프레임 갱신을 사용한다. 렌더 해상도·그림자·후처리를 기기별로 줄이고 저사양/움직임 줄이기 모드를 제공한다. CSS만으로 실제 동적 조명이나 물리적인 반사를 구현한다고 가정하지 않는다.

## 온라인 연출에서 먼저 정리할 부분

현재 보상 캡처는 본인 행동 요청과 `confirmedAction` 중심이다. 상대 행동도 생생하게 보이려면 확정 상태 변화에서 모든 좌석의 시각 이벤트를 구성해야 한다.

- 게임 상태와 연출 상태를 분리한다. 연출이 취소돼도 서버 상태·턴·보석 수량은 바뀌지 않는다.
- 확정 버전의 이전/이후 공개 상태를 비교해 칩 이동·구매·시장 보충 이벤트를 만든다. 본인만 개인 예약 뷰를 추가 사용한다.
- 버전/이벤트 키로 한 번만 재생하고, 초기 구독·새로고침에서는 현재 보드를 즉시 그린다.
- 버전을 건너뛰거나 재접속하면 긴 과거 연출을 재생하지 않고 최신 상태로 맞춘다.
- 상태 차이만으로 예약 방식 등 정확한 행동을 판별할 수 없으면 단순 상태 전환으로 표시한다. 정확한 재생이 꼭 필요할 때만 서버에 최소한의 공개 행동 이벤트를 추가한다.
- 공개 이벤트에 덱 순서·상대 비공개 예약 카드 ID를 포함하지 않는다. 상대 예약은 뒷면으로 표현한다.
- 상대가 다음 턴을 먼저 진행해도 연출 큐가 상태를 되돌리거나 무한 대기하지 않도록 최신 버전으로 수렴시킨다.
- DOM 이동에서 사용하는 `getBoundingClientRect()`는 화면 좌표다. 테이블 기울기 도입 후 다시 검증한다. WebGL 확장 시 화면/월드 좌표 변환 계층으로 교체한다.

## 진행 순서와 대략적인 규모

아래는 숙련 개발자 1명, 기본 테마 우선, 기존 그림 재사용을 가정한 작업일 추정이다. 모델·음원 제작, 대규모 디자인 수정, 실제 기기 성능 문제에 따라 늘어날 수 있다.

1. **공통 보드와 시각 상태 정리: 2~3일.** 로컬/온라인 상태를 공통 표시 모델로 변환하고, 통신·입력과 표시를 분리한다. 로컬 기준 프로토타입을 만든다.
2. **A안 2.5D 재질과 부품: 3~5일.** 펠트/목재 배경, 카드 앞뒤/단면, 덱 층, 칩 스택, 그림자와 호버. 테마별 그림과 자원 색을 유지한다.
3. **C안 행동·상대 연출·소리: 3~5일.** 확정 이벤트 큐, 보석 이동, 결제/획득/보충 순서, 귀족·턴 표시, 음량·음소거. 첫 사용자 입력 후 오디오를 활성화한다.
4. **모바일·접근성·온라인 회귀 확인: 2~4일.** 좁은 화면에서는 기울기를 줄이고 카드 확대와 하단 행동 트레이를 쓴다. 소리/움직임 설정을 저장한다.

**첫 배포 가능한 2.5D 범위: 약 10~17작업일.** 이후 B안 실제 3D는 대표 보드 한 화면을 먼저 3~5일 검증하고, 품질이 확인되면 추가 약 10~20작업일 규모로 계획한다. 이는 확정 견적이 아니다.

## 파일 단위 작업 초안

- `pages/MultiplayerGamePage.tsx`, `pages/GameBoardPage.tsx`: 온라인/로컬 상태·입력 연결을 유지하고 공통 보드 렌더러 호출.
- 신규 `components/board/BoardScene.tsx`, `BoardHud.tsx`, `BoardCard.tsx`, `TokenStack.tsx`: 테이블·부품·정보 패널 분리.
- 신규 `animations/boardEvents.ts`, `boardTimeline.ts`: 확정 상태 차이와 연출 큐·중단·중복 방지.
- 기존 `animations/boardReward.ts`, `marketDeal.ts`: 이동과 배분 동작을 공통 타임라인에 연결.
- 신규 `services/gameAudio.ts`: 사용자 입력 후 활성화, 이벤트별 효과음, 음량·음소거.
- `styles.scss`에서 보드·카드·칩·HUD·모션 스타일을 모듈로 나누고 공통 재질/그림자 토큰 도입.
- `assets/board/`, `assets/audio/`: 압축한 재질 텍스처와 짧은 효과음. 콘셉트 이미지를 통째로 게임 배경으로 사용하는 방식은 피한다.
- 실제 3D 결정 시 신규 `components/board3d/`에 Canvas 렌더러를 만들고 공통 표시 모델·HUD를 재사용.

## 완료 기준

- 기본 2~4인 게임에서 12장 시장·점수·비용·은행·내 자산을 쉽게 읽고 조작할 수 있다.
- 보유 보석과 영구 할인이 시각적으로 구분되며, 6색은 색 외에 기호로도 구분된다.
- 두 클라이언트에서 구매·예약·보석 획득·반환·귀족·턴 전환이 각 한 번 재생된다.
- 실패한 행동에는 성공 연출이 없고, 중복 응답·재시도·재연결로 칩과 점수가 중복 표시되지 않는다.
- 비공개 예약·덱 정보가 연출 데이터나 공개 뷰에 노출되지 않는다.
- 페이지 이동·빠른 상태 변경·움직임 줄이기에서 연출을 취소해도 입력이 정상 복구된다.
- 데스크톱 1440×900, 노트북 1280×720, 모바일 390×844에서 확인한다. 키보드와 터치로 카드 상세·확정·취소가 가능하다.
- 목표 성능은 대표 데스크톱 60fps, 낮은 품질의 대표 모바일 30fps 이상으로 두되 실제 기기에서 측정해 판단한다. 게임판이 멈춰 있을 때 불필요한 렌더링을 줄인다.
- 기존 엔진 테스트, 타입 검사, 빌드와 에뮬레이터 멀티플레이 검증을 수행한다. 추가 테스트는 이벤트 중복·버전 건너뛰기·취소 등 새 동작을 검증한다.
